# v0.2.1 additive migration recovery verification

Folderbase Core v0.2.1 is a crash-safety patch for additive migrations. It
does not change the protocol version or approve any proposed streaming,
Folderbase Version/Remote Head, or mutation source-identity contract.

## RED evidence

The recovery tests were extended one public lifecycle seam at a time before
each implementation change:

1. `JournalPrepared` was added to the durable checkpoint set. The test failed
   because additive apply could reach `applying` before a journal existed.
2. A simulated exit immediately after migration-directory preparation made a
   retry fail with `WouldOverwrite(.../staging)`.
3. A post-staging checkpoint initially never fired.
4. A simulated exit after a fully synced temporary journal initially never
   fired, exposing the direct-to-final torn-write window.
5. A journal collision deleted an unowned staging sentinel.
6. A staging collision left both the plan and journal in `applying`.

Representative red output:

```text
assertion failed: interrupted.is_err()
called `Result::unwrap()` on an `Err` value:
WouldOverwrite(".../.folderbase/migrations/<id>/staging")
left: Applying
right: RolledBack
```

## GREEN evidence

The fixed implementation now:

- publishes the initial journal from a fully written and synced
  same-directory temporary file using atomic no-clobber hard-link semantics;
- changes the durable plan to `applying` only after the journal exists;
- creates staging only after recovery state is durable;
- retries the approved plan after a pre-publication interruption, even when a
  stale temporary journal remains;
- reopens and rolls back after every durable additive checkpoint;
- records a staging-creation failure as `rolled_back`; and
- never removes bytes from a staging directory the current apply did not
  create.

